\section{Designing for the High-Pressure Industrial Environment}
%----------------------------------------------------------------------------------------

Drishti is designed for operators already performing wheat quality assessment in high-pressure warehouse conditions. The device must integrate into an existing workflow, not replace it.

Operators at the warehouse site manage truck queues, work with fine dust on all surfaces, and handle grain under conditions that are physically demanding. The interaction model was designed against that operational reality \cite{Stanton2005, Norman2013}. The goal is to reduce the number of decisions an operator must make explicitly, without removing their agency.

Two interaction layers were addressed: the \textit{physical layer} covers loading, unloading, and maintaining the device; the \textit{digital layer} covers how the system communicates results and what actions the operator must take.

\section{Iterative Design of the Physical Interface}
%----------------------------------------------------------------------------------------

The grain tray is loaded and unloaded with every assessment, up to forty times per shift. Tray interface design therefore received significant attention.

The first iteration was a drawer mechanism with guide rails and magnetic retention. It was rejected for three reasons: solenoid magnetic fields destabilised the retention force; guide rails absorbed plunger energy, reducing impulse effectiveness; and fine wheat dust accumulated in the rail channels across a shift, progressively stiffening the mechanism.

The finalised design uses vertical tray placement: the operator places the tray directly downward onto four plunger apertures. The motion takes under three seconds once learned. There are no channels for dust to accumulate in.

\section{The Digital Dashboard: Information Hierarchy in Practice}
%----------------------------------------------------------------------------------------

The results screen displays classification data across twelve categories, each with a $W/W\%$ value compared against a threshold. Information is structured in three levels of priority. The primary element is the overall verdict (Accept, Reject, or Admin Review), displayed in a large, colour-coded format. The secondary layer shows which categories are out-of-threshold. The tertiary layer provides full category-by-category breakdowns, visible on request.

Three features were designed in direct response to fieldwork observations:

\textbf{One-Touch Testing:} The full assessment cycle launches from a single operator action after tray placement. There are no intermediate confirmations or parameter adjustments. Interruptions in a continuous flow task increase error rate; one-touch launch minimises them.

\textbf{Threshold Visualisation:} Each category result is displayed relative to its acceptance threshold, not as an isolated number. Operators do not need to recall the limit for each category and perform the comparison mentally.

\textbf{Admin Review for Near-Threshold Cases:} Any result within $\pm 2\%$ of threshold triggers an Admin Review flag instead of an automatic verdict. Borderline cases require contextual judgement that the number alone cannot provide. Admin Review routes those cases to expert attention.

\section{Error Visibility and Graceful Degradation}
%----------------------------------------------------------------------------------------

Three failure modes specific to field deployment were identified and addressed in the interface design \cite{Shneiderman2016}.

\textbf{Grain overload detection:} If grain distributes in a configuration that resists dispersion, density monitoring detects the anomalous state and prompts the operator to redistribute before proceeding.

\textbf{Optical contamination alert:} If dust on the imaging surface degrades optical clarity below a reliable threshold, the dashboard flags a cleaning prompt and prevents submission until the operator confirms cleaning.

\textbf{Connectivity status:} Network state is always visible in the status bar. On connection loss, the frame sequence is held in a local queue and resubmitted automatically when connectivity is restored.
